Build window

01

Why this, and why like this

Generative models are confident narrators — fluent and certain whether they're right or not, which is the actual reason people hesitate to fully trust a chatbot's answer. We built it fully offline on purpose. Research papers and internal documents are often sensitive — they shouldn't be uploaded to a cloud LLM or sent through an external API call just to get a summary. Everything here runs through Ollama, locally, on the machine in front of you. No document content, no query, nothing ever leaves that machine. The theory hook came from a research paper we'd read on interactive proof systems, the idea of a Prover generating claims and a Verifier independently checking them — that split is where our Researcher/Verifier agents come from.

Dev Log

The birth of VERITAS, logged as it happened. Every system starts as a blank repo and a deadline — this is the record of how this one got its shape: what worked on the first try, what broke, and what got fixed at 2am.

Kickoff

Picking the problem

  • Reviewed all 5 domain problem statements — picked Gen AI PS1: Autonomous Multi-Agent Research & Fact-Verification System
  • What made it interesting: hallucination isn't a random glitch — it is a genuinely open problem in how these models work
  • Theory hook decided early: interactive proof systems, Prover generates and Verifier checks, mapped onto a Researcher/Verifier agent split
Setup

Repo & naming

  • Created the GitHub repo, local folder, git init
  • .gitignore set up early to exclude models/, docs/, vectorstore_index/ — binary weights and generated indexes have no business in version control
  • Named the project VERITAS — Latin for "truth." Also very close to "Veritaserum," the truth potion from Harry Potter — a small, deliberate nod that stuck once we noticed it.
Layer 1

Single-file offline RAG

Goal before anything clever: prove the boring path works end to end — upload a document, ask a question, get a grounded answer, entirely offline. No fancy agent behavior yet, just the retrieval loop itself, working.

  • Single-file Streamlit app on purpose — one file to reason about, no server/container split eating hours before the core loop is even proven
  • Chunking via RecursiveCharacterTextSplitter, 750 characters with 100 character overlap — the overlap exists specifically so a sentence sliced at a chunk boundary still appears whole in at least one of the two adjacent chunks
  • bge-small-en-v1.5 as the embedding model, loaded locally — converts each chunk into a vector, a fixed-length list of numbers standing in for its meaning. No understanding of language happening here, just a fast, purely geometric comparison: closer vectors mean closer meaning
  • FAISS as the vector store — lowest latency, nothing extra to run alongside it, holds the vectors and searches them fast
  • Strict guardrail prompt: if the answer isn't grounded in retrieved context, the model has to say so instead of guessing
Bug — offline embedding load

First run tried to pull the embedding model from HuggingFace Hub on start — crashed immediately with a connection error, since the whole point is no internet.

Pointed the loader at a local models/bge-small-en-v1.5/ folder instead, loaded straight from disk.

Bug — noisy terminal

Streamlit's file watcher kept scanning unrelated transformer submodules and spamming missing-import warnings for torchvision, drowning out real logs.

Installed torchvision directly rather than disabling the watcher — kept auto-reload working during the rest of the build.

Layer 1 confirmed working — real document, real question, real guardrail trigger, committed to GitHub
Layer 2

The multi-agent pipeline

One model, four roles, each stage checking the one before it.

  • Built all four stage functions — Researcher, Verifier, Contradiction Check, Synthesizer — wired into live st.status() boxes so the pipeline stays visible while it runs
  • Retrieval is currently similarity-only (top 15 by vector distance). A proper cross-encoder rerank is on the Layer 3 list, not done yet
  • Guardrail-skip: if the Researcher finds nothing grounded, Stages 2 and 3 never run
  • Verifier and Contradiction Check run concurrently — neither depends on the other, only on the Researcher
  • Confidence score now reflects the weakest claim in an answer, not an average — one unsupported claim caps the whole score
  • Exception handling added for password-protected, corrupted, and empty files — surfaced by filename instead of silently dropped
  • Full stage history persists — scrolling back up still shows the old breakdown, not just the final answer

Layer 3

Retrieval accuracy, citations, and grounding

Four batches, tested and confirmed working before moving to the next. Everything below actually shipped.

  • FlashRank cross-encoder rerank — retrieval upgraded to a real two-stage pipeline: 15 candidates by similarity, re-scored by a small local cross-encoder for true relevance, top results kept
  • Source citations per claim — every answer ends with a Sources line (doc name + page number), built directly from retrieved chunks in code — so a citation can't be hallucinated
  • Objective grounding check — each claim and its cited evidence both get embedded, and their similarity is computed mathematically — a real check, not the model's opinion of itself
  • Multiple embedding models — three models selectable, each with its own isolated index
Layer 3 batches 1–3 committed to GitHub
Layer 3 — final batch

Multiple vector engines

FAISS and Chroma, both selectable alongside the three embedding models. One Rebuild builds every combination at once, so switching either dropdown afterward is instant — no reprocessing wait.

  • Multi-LLM tested across the same question set — the largest local model correctly declined an out-of-scope question every time; the smallest model occasionally fabricated an answer instead
  • A third vector engine (Qdrant) was evaluated and ultimately dropped — its local-file locking proved too fragile to fully stabilize in the time remaining
Layer 3 complete — committed to GitHub
Final push

Testing, polish, submission prep

The last stretch — no new features, just making sure everything already built actually holds up.

  • Full structured test pass across every stage: guardrail accuracy on out-of-scope questions, fabrication resistance, contradiction accuracy, citation correctness, cross-document comparisons, and file upload/delete
  • Repeated stress-testing of the embedding-model and vector-engine switch — the exact scenario that caused instability earlier — confirmed stable across rapid switching with no lock errors
  • UI pass: consistent help text across every dropdown, cleaner caption formatting, exact branding wording finalized
Late catch — Contradiction Check leaking into the final answer

A last round of testing surfaced the Contradiction Checker occasionally flagging things that weren't real conflicts — two sentences emphasizing different aspects of the same topic, not actually incompatible claims. Worse, this had started leaking into the Synthesizer's final wording, not just staying in its own section.

Decoupled it — the Contradiction Checker still runs, still shown live in its own section, satisfying the requirement in full. But its output no longer feeds into the Synthesizer, so a borderline flag can never quietly reshape the final answer's wording. Its output was also shortened — capped at the clearest few conflicts, one line each — since it no longer needs to be detailed enough for another stage to parse, just clear enough for a person to read at a glance.

Decoupling shipped, committed to GitHub
Deployment

Containerized

Packaged into a single Docker image for a reproducible, one-command setup — no manual Python environment wrangling required.

  • Base image pinned to an exact version rather than a moving "latest" tag — the specific fix for version-drift pain encountered on an earlier offline-RAG build
  • Embedding weights, app code, and Streamlit config all baked directly into the image — runs immediately after docker compose up, no separate download or setup step
  • Documents and the vector index persist outside the container via mounted volumes, so they survive a container restart instead of resetting each time
Image built successfully — 6GB initial size
Final bug hunt

Getting the container actually right

A built image is not the same as a correct one. Running it surfaced three more real issues, each fixed and verified before calling this done.

CPU spike on the largest embedding model

The largest of the three embedding models spiked CPU usage dramatically and took far too long for a live demo — an experience judges would have hit directly.

Dropped it. Two well-tested, fast models beat three where one makes the demo unusable. Image size dropped from roughly 6GB to under 4GB as a direct side effect.

Silently not offline

Despite the whole premise being air-gapped operation, the app was still quietly reaching out to the internet — the embedding library checks for update metadata by default unless explicitly told not to, even when a valid local copy of the model already exists. Invisible with Wi-Fi on, and exactly the kind of gap a judge testing offline-only would hit immediately.

Forced the relevant libraries into offline mode explicitly, at both the code level and the container level — belt and suspenders, so it can't be missed a second time.

Confusing error instead of a clean message

Asking a question before any documents were uploaded surfaced a raw internal file-not-found error instead of a plain "no documents yet" message.

Added an upfront check, and disabled the question box entirely until an index actually exists — prevention instead of an after-the-fact error message.

Rebuilt, verified working with the network disabled — the real test
Submitted

Project complete

Everything planned across four layers is built, tested, documented, and containerized — and genuinely confirmed working offline, not just assumed to be. README, this dev log, and the architecture diagram are all finalized for submission.

The pipeline

One model, four jobs. Verifier and Contradiction Check never see each other's output — only the Researcher's — so they run at the same time.

Same underlying model called up to four times per question — each call a different role, not a different model.
